🔍 Critical Security Loopholes & Vulnerabilities
1. The clone3 Seccomp Bypass (High Severity)
In src/seccomp.rs, you allow the clone3 system call (line 183) alongside clone. You also attempt to block CLONE_NEWUSER using an argument filter on clone:

rust


let clone_sc = ScmpSyscall::from_name("clone")?;
f.add_rule_conditional(
    ScmpAction::Errno(libc::EPERM as i32),
    clone_sc,
    &[ScmpArgCompare::new(0, ScmpCompareOp::MaskedEqual(CLONE_NEWUSER), CLONE_NEWUSER)],
)
The Loophole: clone3 does not pass flags via registers. Instead, it takes a pointer to a struct clone_args in memory. Standard Seccomp-BPF cannot dereference pointers; it can only inspect raw register values.
The Risk: A malicious program inside your sandbox can bypass your CLONE_NEWUSER filter entirely by calling clone3 and passing the namespace flags in memory. This allows the agent to spawn nested user namespaces and potentially trigger kernel exploit vectors.
The Fix: You should block clone3 entirely, but instead of returning EPERM, return ENOSYS (Function not implemented). When glibc or other modern runtimes receive ENOSYS on clone3, they gracefully fall back to the classic clone system call, where your argument-level security filters will actually catch and block the namespace creation.
2. Insecure Directory Permissions in Host /tmp (Medium Severity)
In src/mount.rs, the scratch rootfs directory is created under /tmp on the host:

rust


pub(crate) fn create_scratch_root() -> Result<PathBuf, SandboxError> {
    let path = scratch_root_path();
    fs::create_dir(&path).map_err(SandboxError::CgroupCreateFailed)?;
    Ok(path)
}
The Loophole: fs::create_dir creates the directory using standard umask-derived permissions (typically 0755 or 0775).
The Risk: If there are other unprivileged users or processes running on the same host, they can read and traverse your temporary /tmp/sandbox-root-* directory before it is pivoted, or inspect the mounted workspace and sensitive files during execution.
The Fix: Enforce strict permissions (0700 / rwx------) on the scratch directory immediately upon creation using std::os::unix::fs::DirBuilderExt so that only the user running the sandbox process can read or write to it.
3. TTY Escape Sequence & TIOCSTI Injection (Medium Severity)
The sandbox attaches the child to a PTY master/slave pair.

The Loophole: If the host process reads the raw bytes from the PTY master (stdout_bytes) and prints them directly to the host user's terminal without sanitization, the sandboxed agent can output malicious ANSI escape codes or attempt a TIOCSTI ioctl injection (which pushes arbitrary characters back into the host terminal's input buffer).
The Risk: Terminal takeover or arbitrary command execution on the host when a human operator views the sandbox logs.
The Fix: The host-side reader must sanitize the terminal output stream, stripping or escaping dangerous ANSI control sequences before printing them to a host terminal.
🛠️ Operational Hurdles & Limitations
4. Cgroup v2 Delegation Prerequisite
In src/cgroup.rs, you verify that write access is available in the parent cgroup directory:

rust


let probe = parent.join("cgroup.subtree_control");
The Limitation: This assumes the host has already configured cgroup v2 delegation for the unprivileged user running the binary.
The Reality: In standard environments (like standard CI/CD runners, Kubernetes pods, or nested Docker containers), cgroup v2 delegation is rarely configured by default. Out of the box, sandbox-core will fail immediately with CgroupDelegationMissing.
The Recommendation: You should provide an option to run the sandbox in a "cgroups-disabled" degraded mode (sacrificing CPU/Memory limit enforcement while keeping namespace/Landlock filesystem boundaries intact) so users can test it in environments where they do not have administrative control over host cgroups.
5. Landlock ABI Versioning Compatibility
You require Landlock ABI version 2+ (needs Linux kernel 5.19+). While Landlock is standard in modern distributions, older enterprise distros (like RHEL 8 or older Ubuntu LTS releases running older kernels) will fail to run this sandbox entirely.

For this specific corporate environment, sandbox-core (once the security patches are applied) is an excellent fit. You do not need expensive, heavy MicroVMs (like Firecracker).

However, running a process-level sandbox inside a Kubernetes pod (or containerized pod installation) introduces three specific operational challenges you must design for:

1. The Cgroup v2 Permission Wall in Kubernetes (Major Hurdle)
In cgroup.rs, the sandbox attempts to write CPU and memory limits to the host cgroup directory (e.g., /sys/fs/cgroup/...).

The Problem: By default, Kubernetes container runtimes (like containerd) do not mount /sys/fs/cgroup as writable inside your pods, nor do they delegate cgroup controls to unprivileged containers.
The Consequence: When sandbox-core runs inside your pod, it will fail immediately at the cgroup creation step due to lack of write permissions.
The Solution:
Do not run the pods as root/privileged just to fix this; that defeats the purpose of container security.
Instead, modify the library to support a "degraded execution mode" where cgroup limit enforcement is bypassed if cgroup write access is missing. The namespaces and Landlock filesystem limits will still work perfectly, which is usually more than enough for internal users.
2. Nested Containerization (User Namespaces inside K8s)
The sandbox creates nested namespaces (User, Mount, PID) inside the pod by calling clone/clone3.

The Problem: Depending on your Kubernetes cluster configuration and your Pod Security Standards (PSS), the cluster might be configured with a restrictive Seccomp profile (like RuntimeDefault) that blocks clone operations containing certain namespace flags.
The Solution: You must ensure that your Kubernetes pod's deployment manifest allows unprivileged user namespace creation. In your pod's securityContext, you may need to adjust your Seccomp profiles if the default profile blocks namespace creation syscalls.
3. Network Access for Internal Tools
The sandbox currently uses CLONE_NEWNET to completely disconnect the sandboxed process from the network.

The Problem: In a corporate setting, your AI agents might actually need to access internal APIs, query databases, or call external LLM endpoints.
The Solution: If the agents need network access, you will need to disable CLONE_NEWNET in the clone flags so the sandboxed process shares the pod's network namespace, allowing it to route traffic through your pod's standard network interfaces.
